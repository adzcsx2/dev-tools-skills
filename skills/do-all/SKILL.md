> **中文环境要求**
>
> - 面向用户的进度更新、确认提示和执行总结必须使用中文
> - 代码标识符、命令、日志和文件路径保持原文
> - 所有生成文件必须使用 UTF-8 编码且不带 BOM

# Do All

持久、顺序地执行一份已有计划的全部阶段。`all` 已包含在命令名中，不需要额外子命令。

## Parse the invocation

1. 接受以下形式：
   - `/do-all`
   - `/do-all docs/plan/example/00-执行文档.md`
   - `/do-all 按照即将生成的 00-执行文档.md 执行`
   - `$do-all` 及其带参数形式
2. 解析前先规范化输入：
   - 如果参数最前面存在冗余的独立 `all`，将其视为兼容文本并移除；
   - 不得要求用户额外提供 `all`，也不得提示缺少 `all`；
   - UI 在 skill chip 后显示的文本必须视为命令参数；
   - Codex 入口使用 `$do-all`，不得改写为 `$do_all`。
3. 如果存在参数，按以下顺序解析目标计划：
   - 调用中明确给出的文件路径或文档名；
   - 当前对话明确提到的计划路径；
   - 工作区内唯一明显相关的执行计划文档。
4. 如果没有参数（包括 `/do-all`、`$do-all` 或冗余的 `/do-all all`）：
   - 检查当前对话中刚生成、正在生成、承诺下一步生成或明确讨论的计划；
   - 必要时只读检查工作区，确认最可能的执行文档；
   - 将意图推断为“按阶段测试门禁执行该计划的全部内容”；
   - 只有一个明确目标时，简短告知推断出的路径并立即开始，不要求确认；
   - 唯一目标仍在生成时，立即按下方流程等待，不要求用户再次调用。
5. 多个计划同样合理时，列出精简候选并请用户选择。没有可信目标时，说明缺少什么并请求计划路径。不得自行编造目标。

## Wait for a future plan

如果目标计划尚不存在，不得从假设的大纲开始执行。

1. 判断计划由当前工作流、另一代理或进程、还是明确引用的后续步骤生成。
2. 监控精确目标路径。优先使用等待或监控能力；否则以不超过 30 秒的短间隔进行非阻塞检查。
3. 等待期间至少每 60 秒提供一次简短进度更新。
4. 不设置任意超时。只在以下情况停止等待：
   - 用户取消或替换请求；
   - 生成计划的工作流报告失败；
   - 缺少必要权限或外部状态导致无法继续；
   - 无法确定目标路径或生成者。
5. 只有生成者完成，或文件连续两次检查保持稳定且能解析为完整分阶段计划时，才视为准备完成。不得执行部分写入的文件。
6. 如果当前工作流负责先生成计划，生成完成后必须直接继续执行，不要求用户再次调用 `/do-all` 或 `$do-all`。

## Load project instructions and inspect the plan

修改生产文件前：

1. 读取目标文件适用的 `AGENTS.md`、legacy 项目说明和规则。
2. 完整读取计划文档。按文档约定，以计划目录或项目根目录解析相对路径。
3. 按顺序提取全部阶段，包括依赖、文件、验收条件、测试命令、风险和明确的非目标。
4. 创建或更新任务计划，让每个执行阶段都可见，并始终只保留一个 `in_progress` 阶段。
5. 检查计划在当前工作区是否可执行。通过只读检查协调过时文件名或无害漂移；只有缺失决策会实质改变产品行为、数据、安全或范围时才询问用户。
6. 保留用户已有改动和无关工作区改动，不得 reset、覆盖或清理它们。

执行文档是唯一事实源。不得省略阶段、以削弱门禁的方式合并阶段或添加无关范围。如果计划在执行期间发生实质变化，开始下一阶段前必须重新读取，并安全纳入尚未完成的要求。

## Execute every phase

严格按文档顺序执行每个阶段：

1. 只将当前阶段标记为 `in_progress`，并简短说明目标结果和验证目标。
2. 编辑前检查相关实现和现有测试模式。
3. 行为变更在可行时遵循 TDD：
   - 添加或更新一个会因缺失行为而失败的测试；
   - 确认失败具有意义；
   - 实现最小但完整的变更；
   - 在测试保持通过时重构。
4. 完成该阶段的全部项目和验收条件，保持变更范围聚焦。
5. 审查阶段 diff 的正确性、错误处理、安全性、兼容性和意外的无关变更。
6. 执行阶段测试门禁。
7. 只有门禁全部通过后才能将阶段标记为 `completed`，并立即进入下一阶段。

不得停在描述代码、输出部分 patch 或只完成第一阶段。不得把常规测试交给用户。除非用户或执行计划明确授权，不得 commit、push、deploy、publish，也不得执行破坏性或外部写入操作。

## Enforce the phase test gate

不得越过失败或未验证的阶段。

每个阶段都要执行与变更相关的全部验证：

1. 变更行为的目标单元测试或组件测试。
2. 跨越已修改边界的相关集成测试。
3. 邻近现有行为的回归测试。
4. 适用于相关文件的类型检查、lint、格式检查、schema 校验或构建检查。
5. 关键用户流程或 UI 行为变化所需的 E2E 或视觉验证。
6. 项目支持时执行覆盖率检查；达到项目阈值，或适用规则要求的 80%。

使用项目记录的测试命令。当 `~/.claude/scripts/auto-test-loop.js` 存在且适用规则要求使用时，通过以下方式执行：

```text
node ~/.claude/scripts/auto-test-loop.js "<test command>" 3
```

根据结果处理：

- Pass：记录命令和证据，然后进入下一阶段。
- Fail：诊断并修复实现，或修正已证明错误的测试，然后重新运行完整阶段门禁。
- Flaky：消除不确定性来源，不得把偶然通过作为证据。
- 没有自动测试：可行时添加测试；非代码产物执行最强的确定性验证，例如解析、lint、链接检查、渲染或制品检查。
- 环境或外部依赖失败：穷尽范围内的安全替代方案；确实无法继续时停在当前阶段，报告精确阻塞和恢复条件，不得标记通过。

辅助脚本的 retry 上限只限制单次调用，不限制完成任务的责任。有具体修复或新假设时继续诊断并重新调用；不得在没有新证据时重复同一个失败操作。

## Finish the complete plan

所有阶段门禁通过后：

1. 运行仓库完整相关测试套件，而不只是最后阶段的测试。
2. 运行完整适用的 build、typecheck、lint 和覆盖率检查。
3. 按每个计划阶段和验收条件执行最终 diff 审查。
4. 确认未引入 secrets、调试制品、临时文件或无关改动。
5. 只有计划文档原本定义了状态跟踪时，才更新其中的 checkbox 或执行状态；不得创建重复状态文档。
6. 只有所有阶段与最终检查都通过后，才可标记任务完成。

最终报告必须简洁包含：

- 已完成的全部阶段；
- 重要变更文件或行为；
- 各阶段与最终验证命令及通过结果；
- 明确授权的计划偏差；
- 只有确实无法完成时才列出遗留阻塞。

不得把跳过、失败或未运行必需测试的任务声明为成功。
